## Запуск тестов

Нужен Node.js 20+.

```bash
npm ci                       # Playwright и TypeScript
npm run app:install          # зависимости магазина (для локального прогона)
npx playwright install chromium

npm test                     # все тесты; магазин поднимается автоматически на :3100 с чистыми данными
npm run report               # HTML-отчёт (трейсы, скриншоты и видео упавших тестов)
npm run test:ui              # интерактивный режим
```

**Против развёрнутого стенда** (ничего не сбрасывает, тестовые данные уникальны для каждого теста):

```bash
BASE_URL=__SHOP_URL__ npx playwright test --project=chromium
```

Полезное:

```bash
npx playwright test tests/e2e/checkout.spec.ts      # один файл
npx playwright test --grep @smoke                   # только смоук (desktop + mobile)
npx playwright test --repeat-each=3                 # проверка на флаки
npm run typecheck                                   # tsc --noEmit
```

Результат локального прогона: **94 passed** (88 тестов в desktop Chromium + 6 смоук-тестов на мобильном вьюпорте Pixel 7);
`--repeat-each=3` — 282/282, флаков нет.

## Подход к тестированию

- **Изоляция.** Каждый тест работает в своём browser context — у него своя cookie-сессия и, значит, своя корзина.
  Пользователи создаются уникальными (`e2e-<uuid>@example.com`). Тесты не зависят друг от друга
  и выполняются параллельно (`fullyParallel`).
- **Воспроизводимость.** Локально Playwright сам запускает магазин из `./app` во временном `DATA_DIR`
  с `ALLOW_TEST_RESET=1`, а `global-setup` сбрасывает данные. Против внешнего стенда (`BASE_URL`) reset не вызывается:
  тесты заказывают товары с большим остатком, а цены и остатки берут из API, а не хардкодят.
- **Arrange через API, проверки через UI.** Фикстура `api` использует `page.request` — cookie общие с вкладкой,
  поэтому корзину можно наполнить API-вызовом и сразу проверять её на странице. UI проходится целиком
  только там, где это и есть предмет теста (смоук-сценарий «каталог → корзина → оформление»).
- **Page Object Model** и локаторы по ролям и подписям (`getByRole`, `getByLabel`) — это заодно
  проверка доступности. Где это нужно, используются `data-testid`, которые есть в разметке.
- **Без sleep.** Ожидания — web-first assertions и `waitForResponse` на конкретный запрос
  (поиск с debounce, пересчёт корзины, расчёт доставки).
- **JS-ошибки на странице роняют тест** (фикстура `page` собирает `pageerror`).
- **Граничные значения** подобраны по реальным ценам каталога: корзина ровно на 3000 ₽ (порог бесплатной доставки),
  3000 ₽ после скидки, ровно 2000 ₽ для `WELCOME500`.
- **Найденные баги зафиксированы тестами** в `known-bugs.spec.ts`. Тест описывает *ожидаемое* поведение
  и помечен `test.fail()`: пока баг есть, прогон зелёный, а в отчёте видна аннотация `bug`. Когда баг исправят,
  тест неожиданно пройдёт — Playwright подсветит это, и пометку нужно снять. Я проверил, что каждый такой тест
  падает именно из-за бага, а не из-за ошибки в самом тесте.
- **Артефакты для разбора:** trace, скриншот и видео сохраняются для упавших тестов.

### BUG-01 🟠 Количество 0 (или пустое поле) добавляет в корзину 1 шт.

- **Шаги:** карточка товара → в поле «Количество» ввести `0` (или очистить поле) → «Добавить в корзину».
- **Ожидание:** ошибка «Некорректное количество», корзина не меняется (отрицательные значения именно так и обрабатываются).
- **Факт:** «Товар добавлен в корзину», в корзине +1 шт. То же через API: `POST /api/cart/items {"qty": 0}` → 201.
- **Причина:** `server.js:282` — `Number(body.qty || 1)`: `0` и `""` ложны и заменяются на 1 до валидации.

### BUG-02 🟠 Промокод «оживает» в новой корзине

- **Шаги:** добавить товар на 2000 ₽ → применить `WELCOME500` → удалить товар кнопкой «Удалить»
  (корзина пуста, поле промокода пустое) → позже добавить товары на 4000 ₽.
- **Ожидание:** скидки нет — пользователь промокод не вводил.
- **Факт:** скидка −500 ₽ применяется автоматически. Так же скидка молча пропадает и возвращается,
  когда сумма проходит через порог 2000 ₽, а поле промокода при этом очищается.
- **Причина:** `session.promo` сбрасывается только в `DELETE /api/cart` и после заказа, но не при удалении последней позиции.

### BUG-03 🟠 Поиск не учитывает ё/е

- **Шаги:** в поиске ввести «черный».
- **Ожидание:** найден «Чай Ассам» («Крепкий чёрный чай…»). Большинство пользователей не печатает «ё».
- **Факт:** «Ничего не найдено». По запросу «чёрный» товар находится.
- **Причина:** `server.js:221-222` сравнивает строки без нормализации `ё → е`.

### BUG-04 🟠 Валидация телефона пропускает строку без цифр номера

- **Шаги:** оформить заказ с телефоном `7---------` (или `7(((((((((`).
- **Ожидание:** ошибка «Укажите телефон в формате +7 900 000-00-00».
- **Факт:** заказ создан с непригодным для связи номером.
- **Причина:** регэксп `^\+?\d[\d\s()-]{9,15}$` требует одну цифру, остальное могут быть разделители. Нужно проверять количество цифр (10–11).

### BUG-05 🔴 Некорректная cookie роняет API с 500

- **Шаги:** `curl -H 'Cookie: sid=%E0%A4%A' <host>/api/products`
- **Ожидание:** 200 (битая cookie игнорируется, выдаётся новая сессия).
- **Факт:** `500 Внутренняя ошибка сервера` на **всех** `/api/*`, включая `/api/health`. Пользователь с такой cookie
  (её мог поставить соседний сервис на том же домене, расширение браузера или злоумышленник через поддомен)
  не может пользоваться магазином, пока вручную не очистит cookie. Health-check с такой cookie показывает сервис «упавшим».
- **Причина:** `server.js:140` — `decodeURIComponent` без `try/catch` бросает `URIError`.

### BUG-06 🔴 Утечка памяти: сессия на каждый запрос без cookie

- **Шаги:** 20 раз выполнить `curl <host>/api/health` → посмотреть `shop_active_sessions` в `/metrics`.
- **Ожидание:** запросы без состояния (health-check, мониторинг, боты, API-клиенты без cookie jar) не создают сессий.
- **Факт:** +20 сессий. `Map` сессий в памяти растёт бесконечно: TTL и очистки нет, `Max-Age` есть только у cookie.
  Это медленная утечка памяти и тривиальный DoS. Заодно метрика «Активные сессии» показывает мусор.
- **Причина:** `server.js:145-151` создаёт сессию на любой запрос к `/api` без валидной cookie.
  Решение: создавать сессию лениво (при первой записи в корзину или логине) и добавить TTL с очисткой.

### BUG-07 🟡 «+» на карточке товара не ограничен остатком

- **Шаги:** открыть «Чайник с гусиным носиком» (в наличии 3) → нажать «+» 5 раз.
- **Ожидание:** количество не больше 3 (у поля есть `max="3"`, но кнопка его игнорирует).
- **Факт:** 6. Ошибку пользователь узнаёт только после нажатия «Добавить в корзину».

### BUG-08 🟡 Пароль из одних пробелов

- **Шаги:** регистрация с паролем `"      "` (6 пробелов).
- **Ожидание:** ошибка валидации пароля.
- **Факт:** аккаунт создан. Имя при этом обрезается (`trim`), а пароль нет — правила непоследовательны.

### BUG-09 🟠 Session fixation: идентификатор сессии не меняется при входе

- **Шаги:** запомнить cookie `sid` гостя → войти → сравнить `sid`.
- **Ожидание:** после аутентификации выдаётся новый идентификатор сессии (OWASP Session Management).
- **Факт:** `sid` тот же. Если злоумышленник смог подсунуть жертве свою cookie, после входа жертвы он получает её авторизованную сессию.

### BUG-10 🟡 После выхода заказ остаётся доступным в этом браузере

- **Шаги:** войти → оформить заказ → «Выйти» → открыть `#/order/<id>`.
- **Ожидание:** «Заказ не найден» — после выхода персональные данные (имя, телефон, адрес) не показываются.
- **Факт:** заказ виден: доступ проверяется по `sid`, а он после выхода не меняется. Это проблема на общих устройствах.

### BUG-11 🟡 API принимает нечисловые значения количества

- `POST /api/cart/items {"qty": "1e1"}` добавляет 10 шт., `{"qty": true}` — 1 шт. Ожидание: 400 «Некорректное количество».
  Причина — неявное приведение через `Number()`.

### BUG-12 🟠 Гость видит кнопку «Выйти»

- **Шаги:** открыть магазин без входа.
- **Ожидание:** в шапке «Войти» и «Корзина».
- **Факт:** рядом с «Войти» видна кнопка «Выйти». Нажатие показывает «Вы вышли».
- **Причина:** у кнопки стоит атрибут `hidden`, но правило `button { display: inline-block }` из `style.css:29` перебивает его.
  Решение: глобальное `[hidden] { display: none !important; }`.

### BUG-13 🟠 При самовывозе поле адреса не скрывается

- **Шаги:** оформление заказа → выбрать «Самовывоз».
- **Ожидание:** поле «Адрес доставки» скрыто (так задумано: `address-row.hidden = true`).
- **Факт:** поле остаётся на экране. Покупатель может решить, что адрес нужен, или ввести его зря — при самовывозе адрес не сохраняется.
- **Причина:** та же, что у BUG-12: `.form label { display: grid }` перебивает `hidden`.

### BUG-14 🔴 На мобильных нет навигации

- **Шаги:** открыть магазин на экране ≤ 720px (телефон) и войти.
- **Ожидание:** доступны «Каталог» и «Мои заказы».
- **Факт:** `@media (max-width: 720px) { .nav { display: none } }` скрывает меню целиком без бургер-меню.
  Пользователь телефона не может попасть в историю заказов (только набрав `#/orders` вручную).

### Наблюдения (не баги функциональности, но важно для продакшена)

- `GET /metrics` доступен всем без авторизации и раскрывает выручку, число заказов и неудачных входов.
  Его стоит закрыть или отдавать только во внутреннюю сеть. В этом стенде Prometheus тоже собирает метрики по приватной сети.
- Нет ограничения попыток входа — пароли можно подбирать. На дашборде есть панель «Неудачные попытки входа» с порогом.
- Корзины и сессии хранятся в памяти: каждый рестарт или деплой разлогинивает всех пользователей и очищает корзины.
- `app.set('trust proxy', true)` доверяет `X-Forwarded-For` от любого клиента.
- Исходный `Dockerfile` копирует только `package.json` без lock-файла, поэтому сборки невоспроизводимы.
  В `Dockerfile.railway` используется `npm ci`.
- Процентная скидка округляется `Math.round` — при нечётных суммах скидка может быть на 1 ₽ больше 10 %.

## Мониторинг: Prometheus + Grafana

Prometheus собирает `/metrics` магазина раз в 15 секунд по приватной сети Railway. Grafana поднимается
с уже настроенными datasource и дашбордом (provisioning). Дашборд — домашняя страница, открывается по ссылке
без логина (анонимный доступ только на просмотр).

Дашборд «Лавка — магазин» — три блока:

1. **Бизнес** (за выбранный период): заказы, выручка, средний чек, регистрации, товары не в наличии,
   активные сессии; заказы по способу доставки и оплаты; выручка во времени;
   «корзина → заказ» (падение заказов при стабильных добавлениях — признак поломки оформления);
   неудачные входы с порогом (сигнал подбора паролей).
2. **HTTP (RED)**: доступность (`up`), RPS, доля 5xx и 4xx, p95 задержки, аптайм процесса
   (сброс = рестарт: сессии и корзины потеряны); RPS по маршрутам; ответы по классам статусов;
   p50/p95/p99; p95 по маршрутам; ошибки по маршрутам.
3. **Node.js**: CPU, память (RSS, heap — рост без спада = утечка, см. BUG-06), задержка event loop
   (синхронные `scryptSync` и `writeFileSync` блокируют его), GC, активные хэндлы.

Счётчики магазина живут в памяти процесса и обнуляются при рестарте. Поэтому везде используются
`increase()`/`rate()`, которые корректно обрабатывают сброс счётчика.

## Деплой

Railway, три сервиса в одном проекте:

| Сервис | Источник | Особенности |
|---|---|---|
| `shop` | `app/` (`Dockerfile.railway`) | публичный домен, том `/data` для `db.json`, healthcheck `/api/health` |
| `prometheus` | `monitoring/prometheus/` | только приватная сеть, том `/prometheus`, `SHOP_TARGET=shop.railway.internal:3000` |
| `grafana` | `monitoring/grafana/` | публичный домен, `PROMETHEUS_URL=http://prometheus.railway.internal:9090`, пароль админа в переменной `GF_SECURITY_ADMIN_PASSWORD` |

Локально весь стенд поднимается одной командой (нужен Docker):

```bash
docker compose up -d --build
# магазин http://localhost:3000 · prometheus http://localhost:9090 · grafana http://localhost:3001
```
